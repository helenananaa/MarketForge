## 4. F1：控制操作持久化幂等

涉及：`exchange-server/src/{lib,journal,journal_worker}.rs`、migrations、API 契约。

### F1.1 固定幂等协议

- [x] 列出控制端点，至少包括单步、显式推进、暂停、恢复、关闭；标注现有客户端是否发送 key。
- [x] key 作用域固定为已认证主体、房间、控制 key；与订单 key 空间的关系在协议中明确。
- [x] 指纹包含操作名、规范化参数、协议版本；不能只比较 URL 或未经规范化的 JSON 文本。
- [x] 同键同请求返回原结果；同键不同请求返回 409；仍须检查当前访问权限后才能返回缓存结果。
- [x] 定义成功、业务拒绝、基础设施失败的保存策略，确保失败不会被错误缓存为成功。
- [x] 首版不自动过期有副作用的控制 key；若引入保留期，必须明确过期后的重试语义。

交付物：更新 `docs/API_CONTRACT.md` 和 `docs/RUNTIME_CONTRACT.md`。

### F1.2 接入原子持久化边界

- [x] 复用 0013 表；需要字段或唯一约束时新增迁移，不修改已应用迁移。
- [x] 在同一受控提交路径内完成 key 判重、权限/租约核验、候选状态计算、结果保存和 mutation 写入。
- [x] 并发同键请求不能在锁外查询后分别执行；数据库唯一约束作为最终保护，命中后返回已存结果。
- [x] 单步若由多个 durable 子步骤组成，使用持久化操作 ID 和进度关联每一子步骤；不能在全部副作用后另写幂等结果。
- [x] 数据库提交成功后安装候选状态，再对外发布；客户端取消不能取消提交后的安装。
- [x] 重启或接管能查到原请求；仅有内存缓存不得成为真相来源。
- [x] 内存 journal 提供同进程等价行为，但明确其不承诺进程重启持久化。

### F1.3 故障与并发验收

- [x] 同进程串行重复、至少两个并发同键请求：只产生一次逻辑推进。
- [x] 同键不同 steps/操作：409，无额外 mutation。
- [x] 提交前数据库失败：状态不变，重试可正常完成。
- [x] 提交后响应丢失、进程被终止：恢复重试得到原响应，时钟、订单和策略状态不重复推进。
- [x] 实例 A 提交后由 B 接管：B 重试返回原结果；旧 fencing token 无法追加副作用。
- [x] 查询已完成请求时权限已被撤销：不得泄漏原响应。

**F1 门槛**：使用真实 PostgreSQL 和真实进程中断验证单步严格一次效果。仅验证重复 pause 不足以通过。
