# MarketForge 后端开发执行计划

基线日期：2026-09-06。本文按当前源码和仓库文档制定，所有步骤初始状态均为未完成；源码中存在实现不代表本轮已运行测试或验证部署。

目标：在不开发前端的前提下，交付一个可通过 HTTP、CLI 和自动化脚本操作的交易训练后端，支持确定性机器人、训练任务、可验证复盘，随后扩展多人权限与外部策略。

## 1. 范围、基线与执行规则

### 1.1 当前可复用的实现

| 能力 | 主要入口 | 本计划的处理方式 |
| --- | --- | --- |
| 撮合、订单类型、现货与永续、风控清算 | `exchange-core/src/{engine,actor,spot,perp,risk,trading}.rs` | 保留现有语义，新增任务必须走交易入口 |
| 多市场、多场所、资产与划转 | `exchange-core/src/{room,simulation,portfolio,transfer}.rs` | 第一训练任务只使用单现货市场，继续保留回归覆盖 |
| 规则机器人与参与者 | `exchange-core/src/{agents,participant,gateway,clock}.rs` | 增加受限观察、确定性调度和状态恢复 |
| HTTP、认证、日志、幂等、租约 | `exchange-server/src/{lib,auth,journal,journal_worker}.rs` | 复用提交后安装状态、fencing 和权限边界 |
| 完整执行时间线与 SSE | `exchange-server/src/lib.rs`、`docs/BACKEND_STORAGE.md` | 保留管理员审计接口，另建普通用户订阅契约 |
| CandleScope 本地与远程适配 | `marketforge-candlescope-plugin` | 保持契约兼容，复用后端结果；暂不扩展 UI 或上架流程 |

### 1.2 已确认的缺口

1. 服务端机器人通过 HTTP 回调自身，在 Bearer 模式下被显式禁止。
2. `AgentRuntime` 有自己的时钟，服务端 worker 按墙钟休眠；需要统一权威仿真调度语义。
3. `Participant` 尚无通用版本化状态保存契约；命令重放一致不能证明机器人恢复后继续决策一致。
4. 当前 `MarketView` 包含账户集合，不能直接成为外部代理的公开观察协议。
5. 周期 snapshot 没有接入新房间的 `StateCheckpoint` 恢复加速路径。
6. 完整执行 SSE 是管理员接口；用户自己的订单流和公开行情流仍需独立设计。

### 1.3 本轮不包含

- React 页面、图表组件、登录页面、可视化回放和排行榜页面。
- 新交易品种的大规模扩展、更多复杂订单类型、真实资金或实盘交易。
- LLM 实时决策、强化学习训练、Kafka、ClickHouse、Kubernetes。
- 全库重写或提前把所有房间改为分布式 actor。

CLI、JSON 报告、HTTP 契约及测试夹具属于本轮后端交付范围。

### 1.4 每步的执行方式

1. 开始前记录当前 commit、工作区状态及前一步验收证据；保留无关修改。
2. 每个编号步骤形成一个可独立审查的变更；相邻小步骤可合并，但不得跳过验收门槛。
3. 先明确协议、顺序和失败语义，再实现；数据库变更使用新增版本迁移。
4. 完成对应测试后，记录结果、实际命令、跳过项和限制，再勾选步骤。
5. 阶段门槛未通过时修复本阶段，不提前依赖未完成能力。
6. 表中的新文件、类型、命令和接口是建议交付契约，尚不存在；实现前允许结合现有结构调整，并同步更新本文。

## 2. 阶段依赖与里程碑

```text
P0 基线与契约
  → P1 统一命令入口、仿真时钟与可恢复机器人
  → P2 无界面的交易与数据接口闭环
  → P3 第一个可评分训练任务
  → P4 检查点、历史回放与证据报告
  → P5 多人权限与外部策略平台
  → P6 持续运行与发布验收
```

- **M1：P0–P2**：Bearer 模式可操作房间、运行机器人、交易并恢复连接。
- **M2：P3–P4**：低滑点买入训练可以结束、评分、重放和复核，作为第一个产品交付点。
- **M3：P5–P6**：多人和外部策略可用，具备运行与故障恢复证据。

先完成 M2 再决定扩大部署规模。M2 之前不以吞吐优化代替训练能力交付。

## 4. P1：统一执行入口与确定性机器人

### P1.1 提取共用交易应用层

涉及：`exchange-server/src/lib.rs`，建议新增 `application.rs`、`agent_worker.rs`。

- [x] 把 HTTP handler 内的认证主体解析后流程提取为共用应用服务。
- [x] 人类请求和机器人请求均经过：身份与账户授权 → 房间归属/租约 → 风控与撮合 → 日志事务 → 安装候选状态 → 发布结果。
- [x] 内部机器人使用由服务端绑定的参与者身份及账户权限，禁止信任机器人提交的任意 user/account ID。
- [x] 保留订单 ID 分配、幂等、拒单记录、附带清算执行和 journal 原子性。
- [x] 将 worker 的 HTTP 自回调替换为内部入口，完成后再解除 Bearer 模式的 worker 限制。

验收：同一交易经 HTTP 与内部入口得到相同业务结果；越权请求拒绝；数据库失败不安装候选状态；客户端取消不能打断提交/安装区间。
记录：worker 改为 `commit_scheduler_step` 内部入口（`OrderGateway::new_scheduler` + 既有 journal-then-install）。未拆出独立 `application.rs` 文件，逻辑放在 `lib.rs` 以免打断现有 handler 可见性。Bearer 可启动 worker。

### P1.2 定义受限参与者观察

涉及：`gateway.rs`、`participant.rs`、`agents.rs`，建议新增版本化 `ParticipantObservation`。

- [x] 观察只包含允许的公开盘口、成交、仿真时间和参与者自己的订单、余额与仓位。
- [x] 显式指定 instrument，不依赖当前默认主市场的隐式路由。
- [x] 把公开信息与管理员信息分离，不直接序列化完整 `MarketView.accounts`。
- [x] Noise、DCA、Grid 全部迁移到同一观察边界。

验收：增加第二账户的隐私数据不改变首个参与者可见结果；跨品种不会错误下单；策略不能读取未来场景事件。

### P1.3 统一仿真调度

- [x] 用一个权威仿真时钟驱动房间，调度模式分为手动单步和墙钟唤醒的自动步进。
- [x] 固定每步顺序：推进时间与到期结算 → 执行到期场景动作 → 按稳定参与者顺序观察及决策 → 按动作顺序提交 → 更新训练状态。
- [x] 明确参与者顺序采用固定排序；后运行者可观察本步前面已提交的结果。若未来改为同时观察，必须新版本化。
- [x] 人类输入按持久化的受理顺序纳入执行；可复现声明包含相同输入顺序，不能只声明相同 seed。
- [x] 自动唤醒被延迟时不跳过仿真步骤；追赶次数有上限，超限报告落后状态。
- [x] pause 停止自动步进和交易；手动单步仅管理员可在暂停状态触发；close 禁止新交易和后续步进。
- [x] 为时钟溢出、过大 steps、重复推进请求设置显式处理，控制类写入也要支持幂等。

验收：相同输入与配置在不同墙钟速度下结果一致；暂停边界无新交易；手动推进重试不多走一步。
说明：场景到期动作钩子在 P1 为空（P3 填入）；调度顺序已预留该位置。训练状态更新同样待 P3。

### P1.4 保存机器人状态与步骤进度

- [x] 为每类 agent 定义版本化状态，包括 RNG、DCA 计数、Grid 已初始化标志及未完成动作。
- [x] 保存调度步、参与者位置、动作位置及机器人配置版本；不要只保存模板和初始 seed。
- [x] 决策先在候选状态中执行。将决策后 agent 状态与动作列表持久化为步骤意图，再提交动作。
- [x] 动作使用稳定键，例如 `(run_id, step, participant_id, action_index)`；恢复时根据执行记录与进度避免重复提交。
- [x] 零动作决策也保存状态推进；明确应用层拒绝、业务拒单和临时基础设施失败的进度处理方式。
- [x] agent 状态、动作消费进度和对应执行事务保持一致；不要出现交易提交但动作仍被当作未执行的窗口。
- [x] 旧房间缺少 agent 状态时允许市场历史恢复，但显式标记不能保证策略连续运行，禁止静默重置策略。

验收：分别在决策保存前后、动作提交前后、步骤完成前后注入崩溃；恢复后的命令、成交、账户和后续机器人动作与不中断运行一致。

### P1.5 绑定租约与生命周期

- [x] 只有持有当前房间 fencing token 的实例能步进或驱动 agent。
- [x] lease 丢失、关闭或 shutdown 时停止接受新步骤，完成已提交工作并退出 worker。
- [x] 接管时先恢复市场、调度器和 agent 状态，再启动自动运行。
- [x] 公开 worker 状态及最近错误，区分 paused、running、recovering、failed。

**P1 门槛**：Bearer 部署可运行机器人；崩溃继续运行一致；双实例接管无双重交易。上述场景同时覆盖内存模式和 PostgreSQL 模式的适用部分。
记录：`docs/validation/2026-09-06-p1.md`。

## 6. P3：第一个可评分训练任务

### P3.1 版本化训练配置与生命周期

建议新增 `exchange-core/src/training.rs`、`scenarios/training/`。

- [ ] 定义 `TrainingSpec`：版本、市场配置、seed、agent 集合、受训账户、目标量、期限、费用、场景动作、评分规则版本。
- [ ] 定义 run 状态：Created → Running → Completed / Failed / Aborted；暂停单独记录且不消耗仿真时间。
- [ ] 开始后冻结配置并保存内容摘要；每次运行生成独立 run ID 和房间，首版一房间只承载一个 run。
- [ ] 使用仿真时间触发场景动作，并以交易/配置命令实现，禁止直接修改成交价。
- [ ] 定义同一时刻目标完成、期限到达和错误中止的判定顺序。

验收：开始、完成、终止可幂等；重启不重开任务；结束后目标账户不能继续改变本次成绩。

### P3.2 实现持续做市机器人

- [ ] 加入双边报价、成交后补单、价格偏离撤改单、最大挂单数和库存上限。
- [ ] 报价由公开盘口与自身库存决定，遵守余额、费用、最小单位、自成交和普通账户风险规则。
- [ ] 持久化订单引用与库存控制状态，防止重启后重复铺单。
- [ ] 和 Noise agent 组成最小市场；先固定参数，不引入训练模型。

验收：可持续成交并补充流动性；库存和挂单有界；低余额或单边市场时产生明确行为；恢复后无重复挂单。

### P3.3 交付低滑点买入任务

- [ ] 新增固定版本场景：在 T 个仿真步骤内买入 Q 单位现货。
- [ ] 初始持仓为零，受训账户在任务内仅可买入，禁止卖出、存取款和划转；背景账户按场景配置运行。
- [ ] 限制累计成交量与未成交买单总量不超过剩余目标，避免多张订单造成超买。
- [ ] 记录开始时参考价；建议用最优买卖价中点，无双边报价时拒绝开始，禁止事后选基准。
- [ ] 完成/到期时先冻结任务交易，按固定顺序撤销剩余订单，再生成结算结果。
- [ ] 提供 start、status、abort、result API 与 CLI 命令。

验收：完成、部分完成、零成交、过期、主动中止、重复结束和结束期间并发下单均有确定结果。

### P3.4 实现可核算指标与评分

首版以原始指标为主，综合分采用版本化规则并同时输出分项。

- [ ] 成交量 `q = Σqty`，完成率 `q / Q`。
- [ ] 成交均价 `VWAP = Σ(price × qty) / q`，`q = 0` 时为空。
- [ ] 买入成交滑点 `10,000 × (VWAP - P0) / P0`，明确负值表示相对参考价更优。
- [ ] 总执行成本单独包含手续费；费用和价格乘数量先按 instrument 单位换算，使用整数/定点或有理数计算。
- [ ] 输出完成耗时、费用、拒单数、撤单数及剩余目标。
- [ ] 未完成任务必须标记未完成并应用明确惩罚，不能因为少成交而获得更高质量结论。
- [ ] 每个指标记录输入执行范围、基准来源和规则版本；使用人工可核算小样本断言精确值。

**P3 门槛**：CLI 可运行一场训练并导出结果；指标能手算复核；数据库重启前后结果一致。

## 7. P4：检查点、回放与证据报告

### P4.1 将周期检查点接入恢复

- [ ] 统一 snapshot 与 `StateCheckpoint` 的职责，明确检查点覆盖到哪个命令和 mutation 边界。
- [ ] 检查点包含市场、账户、时钟、待执行划转、agent、调度进度和训练状态，附版本及完整性校验。
- [ ] 在一致的持久化边界写入检查点，只重放其后的命令和 mutations，避免重复清算或遗漏无成交步骤。
- [ ] 不兼容的可选检查点按明确政策回退完整日志；日志或恢复结果不一致必须失败，不能静默接受。
- [ ] 保留旧数据兼容测试，先不删除历史日志。

验收：完整重放与检查点加尾部重放的最终状态一致；测试边界前/后 mutation；记录实际重放条数证明加速路径被使用。

### P4.2 提供只读历史回放

- [ ] 新增隔离的 replay 服务或 CLI，按命令/时间定位、逐步执行、查询历史盘口与账户。
- [ ] 同时重放 commands 和 mutations；时间相同的记录遵守权威排序，不能单按时间排序。
- [ ] 所有操作作用于独立回放状态，不向 live room 下单或启动机器人。
- [ ] 输出状态摘要及首个分歧位置；跨 seed 验证不能替代相同输入的严格比较。

验收：随机选择历史位置，与原运行捕获的状态一致；回放不改变在线房间；大日志使用有界分页。

### P4.3 生成有证据的训练报告

- [ ] 导出 JSON 与 Markdown，包含配置摘要、目标、结果、指标和局限。
- [ ] 逐笔关联受训订单、成交、费用、下单前可见盘口和执行序号。
- [ ] 先用规则解释可验证事实，例如成交吃掉哪些档位、费用占比、撤单导致的未完成量。
- [ ] 区分直接可见事实与推断，不把“流动性减少”直接宣称为操纵或某策略意图。
- [ ] 报告访问和导出遵守账户范围；管理员完整报告使用独立权限。

### P4.4 做连续运行与恢复对照

- [ ] 固定场景分别执行完整连续运行、进程中断恢复、租约接管和不同步进速度运行。
- [ ] 比较命令/事件顺序、最终账户、agent 状态、训练状态及评分。
- [ ] 将故障点、运行版本、输入摘要和差异输出保存为验收证据。

**P4 门槛 / M2**：同一训练可完成、恢复、回放并复算报告；恢复测试不能只验证最终余额。

## 8. P5：多人权限与外部策略平台

### P5.1 房间成员与角色管理

- [ ] 基于现有 users、room_members、account_owners 建立创建成员、邀请/加入、移除和账户分配 API。
- [ ] 定义 owner、instructor、trader、spectator 权限矩阵；不能仅靠隐藏返回字段控制写权限。
- [ ] 初期继续使用现有 Bearer 身份系统，不把完整身份提供商建设作为必要依赖。
- [ ] 对成员变化持久化和审计，撤权后写入、历史查询和存续订阅同时生效。
- [ ] 规定比赛任务开始后账户分配和参数冻结策略。

验收：两个交易者只能操作自己的账户；旁观者只见公开行情；指导者权限不自动等于任意账户交易权限。

### P5.2 外部策略协议与 Python SDK

- [ ] 将 P1 的受限观察与动作类型发布为版本化协议，外部策略不访问数据库或内部 actor。
- [ ] Python SDK 支持配置、观察、下单/撤单、幂等、恢复游标和可信 owner 路由。
- [ ] 定义延迟、超时、每步动作配额和异常行为；外部 I/O 不在撮合临界区内等待。
- [ ] 实时模式记录实际接纳动作以供重放；确定性批量模式要求版本固定的确定性策略或动作夹具。
- [ ] 提供最小策略示例和与内置策略同规则的契约测试。

验收：Python 策略完成同一训练；策略超时不阻塞其他房间服务；伪造账户、超额动作和非法精度被拒绝。

### P5.3 批量仿真与离线比较

- [ ] 新增 headless batch runner，输入版本化场景、策略参数、seed 集合和步数上限。
- [ ] 输出逐 run 指标、失败原因、版本信息和汇总分布，禁止只保留成功样本。
- [ ] 并发执行彼此隔离的房间，单房间顺序不变；支持中断后按 run 恢复。
- [ ] 比较策略时固定场景与 seed 集合，报告完成率、成本分布和不确定性，不只比较平均收益。

**P5 门槛 / M3 功能部分**：多人权限矩阵通过；外部策略可复现地评估；失败 run 可追溯。

## 9. P6：运行验证与发布门槛

### P6.1 建立容量基线

- [ ] 记录硬件、数据库配置、房间数、agent 数、步频、订单速率和数据规模。
- [ ] 测量 p50/p95/p99 命令延迟、调度落后、journal 队列、内存和恢复时间。
- [ ] 增加低基数指标：步骤失败、agent 错误、任务完成/失败、检查点耗时和恢复重放条数。
- [ ] 先报告全局写通道的实际瓶颈；只有证据表明它限制目标负载时，才制定按房间拆分执行器的后续计划。

### P6.2 故障矩阵与持续运行

- [ ] 覆盖数据库不可用、慢读/慢写、进程退出、客户端取消、租约失效、慢订阅者和磁盘/容量限制的适用场景。
- [ ] 明确故障后 readiness、worker 状态、请求错误和恢复动作，禁止自动无限重试。
- [ ] 先执行短时 smoke，再执行声明负载下的 24 小时持续运行，保存命令、资源曲线及异常记录。
- [ ] 验证长日志恢复、缓存有界及正常关停，不以单次测试通过替代持续运行证据。

### P6.3 整理交付

- [ ] 更新 README、存储文档、API 契约、CLI 使用说明和插件兼容说明。
- [ ] 为数据库迁移、版本升级、备份和恢复提供可执行步骤；不承诺未验证的降级兼容。
- [ ] CI 加入新增 Rust crate、Python SDK 的适用检查，以及训练闭环和 PostgreSQL 恢复测试。
- [ ] 发布说明列出已通过的负载、故障场景、运行时长及仍有的限制。

**P6 门槛**：功能、恢复、隔离与持续运行证据齐全，才能称为可部署的训练后端。

## 11. 第一批执行清单

按以下顺序启动，先完成前三项再引入训练模型：

1. **P0.1**：获取测试与恢复基线，记录已有失败。
2. **P0.2**：固定步骤顺序、时间与持久化边界。
3. **P1.1**：提取交易应用服务，移除 worker 的 HTTP 自回调，验证 Bearer 模式。
4. **P1.2**：限制机器人观察并明确 instrument 路由。
5. **P1.3–P1.5**：实现可持久化调度与租约接管，通过故障注入。
6. **P2**：交付 CLI 和交易/数据闭环，完成 M1。
7. **P3–P4**：交付低滑点任务、评分与回放，完成 M2。

执行到 M2 后，依据实际使用反馈决定 P5 的多人管理与策略 SDK 投入比例；前端可在届时基于已验证的契约独立开发。
