## 实现范围

普通 HTTP 订单按 `room + venue` 取得 FIFO 准备通道，共享同一 venue 的账户余额、现货资产和永续保证金的商品仍串行。独立 venue 在房间提交 mutex 外执行现有 OrderGateway 和撮合核心；短提交段检查候选前驱、重新分配房间 command_seq、检查幂等键和房间级外部动作配额、确认日志、安装状态并发布快照。只合并目标 venue，保留期间其他 venue 已经提交的状态。订单 ID 继续使用原有原子范围预留。

每个房间另有读写协调屏障。普通分区订单持有读侧；原有房间事务持有写侧，因此时钟、跨 venue 资金划转、bot 提交、暂停、清算和训练不能与候选准备交错。全局身份/目录/租约管理仍使用目录写屏障。提交段不会再次申请目录或协调读锁，避免等待写侧时的递归读锁死锁。

分区仅用于含至少两个 venue、没有训练记录、没有排队清算或条件/保护订单的普通人工订单。即使自动订单当前休眠也退出分区路径。候选产生自动执行或待重试清算时，丢弃尚未持久化的候选，释放分区通道，再走协调事务重新撮合；不重编号自动订单，不修改系统订单 ID 规则。单 venue、训练、bot 和自动化仍走协调路径。

`SimulationRoom` 对各 venue 使用 `Arc<ExchangeActor>`，快照/候选共享未改变的 venue，写入时复制目标 venue。Serde 的旧对象结构保持兼容。无自动规则时跳过空的保护/条件扫描，避免写时复制未改变 venue。普通协调订单的管理员查询在目录屏障内、房间锁外执行；幂等与配额检查仍在提交段内。

候选使用事务局部执行日志，房间的真实命令游标保存在 `SimulationRoom`，合并时只追加本次执行并保留所有先前历史。回归先写入 300 个命令跨过历史块边界，再从同一快照准备两个 venue 并反向提交，验证最终引擎状态和完整执行历史与串行重放一致。第一版重复复制历史尾段的 34 组阶段回执及源码保留在 `target/room-lock-load/optimization-abba` 和 `optimized-source`，二进制保留为 `prototype.exe`；它们不纳入最终版本性能比较。

本实现仍有房间级日志提交串行段，以及共享的有界 journal 工作线程。它是保留现有房间提交语义的分区准备实现，不是完整撮合集群或按商品独立清算。没有在普通构建里引入压测指标；诊断指标仍由 `bench-execution-timing` 控制。

## 对照方法

使用与上一轮相同的 Rust HTTP 生成器及 `benchmark_room_contention.py`，每组新启 loopback 服务，内存 journal，有限资金独立账户对，零费用，2 次预热/worker，2048 个测量业务循环。挂单撤单是 4096 请求；成交往返是 8192 请求、4096 笔实际成交。并发 1/8/32；现货/永续；单簿、同房间四商品、四房间和同房间四 venue。

新工具 `compare_room_contention.py` 只编排相同负载，按每个配方“旧→新→新→旧”运行。保存二进制/客户端/负载脚本 SHA256、实际请求回执、余额、空订单簿、唯一订单 ID/房间序号、锁阶段、资源和后台 CPU。一轮 ABBA 出现任何编译重叠就整轮退出主要比较，保留并重测，最多四轮；无编译重叠也不等于机器空闲。新旧比较不改变房间拓扑，因此不再用跨房间差异代替拆锁收益。

指标 `room_held` 包括提交快照发布。分区路径的 `order_apply` 发生在房间提交锁外，增加 `venue_wait`、`venue_compute`、`venue_commit`、`venue_fallback` 计数用于验证分区实际使用。管理员查询移出协调锁后，协调路径的 `order_prepare` 不再包含该查询，因此不能单独把其差值当作总成本下降。端到端延迟和相同负载吞吐是主要比较指标。
