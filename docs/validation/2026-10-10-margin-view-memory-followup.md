# 稀疏/密集风险优化：view 与内存同进度复核

结论：原墙钟负载中峰值内存约 75% 的增长没有在同进度对照中复现，主要解释是执行了更多调度工作、保留了更多历史。没有发现风险索引随步骤积累的显著内存回退。普通 view 的原约 30% HTTP P95 回退也未复现；固定状态的快照构造和 JSON 编码没有回退。端到端尾延迟仍有波动，不能把原来的全部延迟差额精确归因于步数。

以本分支“稀疏增量、密集批量，保持风控/强平/恢复行为，做差分验证与性能对照”的范围判断，目标可以收尾。这个判断不等于整服务已获得 1000-bot、40 step/s 容量资格，也不表示所有 view 尾延迟已经解决。

## 基线和方法

- 分支：`codex/incremental-margin-risk`；冻结基线：`f3ab562`，包括开始优化时原目录的核心优化工作快照。本次仍只修改隔离 worktree。
- 同一个 seed=7 的 1000-bot 模板，两个版本使用完全相同的诊断代码和配方。复用生产实时 `Work::Clock` / `Work::Bots` 提交、观察构造和决策缓存逻辑，固定每步轮转 64 个机器人并按确定顺序提交。原异步负载每步约 1–2 次机器人批提交；本测试固定 1 次，避免决策完成顺序和工作量差异混入对照。
- 0、100、300、700 步检查点；ABBA 两轮，共 8 个完整进程、每版本 4 次。各检查点核对完整可持久化市场状态、调度器、时钟、逐步结果链、累计成交顺序摘要及四类 view 的哈希。全部一致；journal 记录数和字节数也全部一致。
- 每点普通/永续 view，各测新连接和长连接 40 次，另加 3 次预热。在每段最后 20 步并发读取 view，记录鉴权和快照构造的服务端耗时；HTTP 另记录连接、响应头、收包、客户端解析耗时。各表值为每轮 P95 的跨轮中位数，不能把各阶段的 P95 相加。
- 诊断 example 通过显式 `risk-benchmark` feature 启用，全局分配器仍为 System，仅增加请求字节/存活字节计数。默认服务没有诊断端点、分配器计数或固定轮转逻辑。计数对应 Rust 请求的布局大小；working set / private bytes 由 Windows 进程计数器记录，两者不是同一指标。
- 第四个进程的首次尝试在测量开始前遇到 Windows `10053` 连接中止，原记录保留。新进程重跑该轮；只复用参数、二进制哈希和业务状态均核对通过的完整轮次。另保留了使用手动完整调度器路径的废弃预检和每步全 roster 决策的预检，它们不用于最终归因。

## 内存结果

| 同进度指标 | 基线 | 优化版 |
| --- | ---: | ---: |
| 100 步存活堆 MiB | 56.345 | 56.377 |
| 300 步存活堆 MiB | 121.070 | 121.101 |
| 700 步存活堆 MiB | 223.066 | 222.850 |
| 700 步执行区间堆峰值 MiB | 236.200 | 236.088 |
| 700 步进程峰值 working set MiB | 396.658 | 397.738 |
| 700 步当前 working set MiB | 263.361 | 262.625 |
| 累计分配/扩容申请量 GiB | 12.848 | 9.419 |
| 累计分配/扩容调用，百万次 | 44.793 | 37.287 |

700 步存活堆减少约 0.10%，进程峰值 working set 增加约 0.27%，属于很小的差异；100/300 步的存活对象差额约 0.03 MiB，也没有持续增长。累计申请量降低约 26.7%，调用次数降低约 16.8%。申请量是新分配及 realloc 正增长的请求字节，不是进程提交内存，也不包含 realloc 搬移时的全部复制量。

两版本在 700 步均有 1403 个 mutation、11387 个 execution。mutation 的 wire 数据为 88,203,066 字节，Vec 容量为 139,156,736 字节（132.710 MiB），最新 snapshot 数始终为 1。仅这些保留缓冲区就占存活堆的约 59.5%；执行历史、投影、当前状态和机器人缓存还会占用其他内存。`InMemoryJournalStore::store_mutation` 会持续保留编码记录；本分支没有改变保留和恢复策略。

原墙钟负载的时钟步数中位数为 392.5→711.5，调度器 revision 为 809.5→1884.5，峰值 working set 为 258.06→452.71 MiB。即使选几乎相同时钟进度的两轮（703→713 步），调度提交也从 1635→1870，增加约 14.4%，峰值从 392.13→446.04 MiB，增加约 13.7%。这说明只匹配 clock.step 仍不够，机器人工作和历史量也必须匹配。

因此原内存增长主要由工作量/历史累积差异解释，不能将约 195 MiB 的中位数差额归因于新增风险索引。上述进程峰值包括双方相同的完整状态导出和诊断请求；只能作这次配对比较，不能与原生产二进制的绝对峰值直接混算。

## view 结果和归因

| 700 步，P95 ms | 基线 | 优化版 |
| --- | ---: | ---: |
| 普通 view，新连接，含客户端解析 | 29.825 | 30.281 |
| 普通 view，长连接，含客户端解析 | 5.927 | 7.339 |
| 永续 view，新连接，含客户端解析 | 30.605 | 36.376 |
| 永续 view，长连接，含客户端解析 | 25.923 | 28.319 |
| 并发提交时普通 view 总耗时 | 27.363 | 28.485 |
| 并发 view 服务端鉴权 | 0.151 | 0.156 |
| 并发 view 服务端快照构造 | 0.228 | 0.236 |

普通新连接 view 的差额约 0.46ms（1.5%），未复现原 21.59→28.13ms 的约 30% 回退。长连接及永续端到端仍有残差，保留在表中，不能隐藏或称为全部消除。

源码和分段计时支持如下解释：view 读取已发布的 `Arc<RoomManager>`，不进入房间的交易写入锁；鉴权仍经过 journal 的串行读任务，在内存模式下与写任务共享 worker。忙时鉴权的中位 P95 几乎相同，没有发现风险优化造成的持续鉴权排队回退。服务端普通/永续快照构造的 P95 都不足 1ms，不能解释几十毫秒的端到端尾部。连接、收包和客户端解析贡献了更大的波动；不构造账户快照的 clock 请求在两版本也出现约 25ms 的尾延迟。

view 响应本身没有显著随进度膨胀：普通响应从约 160.7KB 变为约 160.9KB，永续从约 336.5KB 变为约 342.5KB；两个版本各检查点字节长度和内容哈希相同。快照仍会扫描全部账户，这是既有读接口成本，不是这轮引入的扫描。

为排除 HTTP 干扰，又用此前已差分核对的固定 1000 账户/20 活跃仓位状态，直接构造 book/accounts/perp_price 并进行 JSON 编码。每进程 100 次预热、5000 次计时；ABBA 三轮、每版本 6 次。两版本输出均为 339153 字节且哈希相同：

| 5000 次，跨轮中位数 ms | 基线 | 优化版 |
| --- | ---: | ---: |
| 快照构造 | 547.008 | 475.790 |
| JSON 编码 | 1954.097 | 1775.235 |

该对照没有复现 view 计算/编码回退；每次构造约 0.109→0.095ms，编码约 0.391→0.355ms。它只验证固定状态读路径，没有鉴权、网络、真实异步写竞争，不能把这个中位数差额宣传为生产 view 提速幅度。原 view 差额更符合工作节奏和公共 HTTP/客户端尾延迟波动，现有证据不足以给原 6.54ms 的每一部分分配精确原因，也不能推断所有永续 HTTP 残差都由步数造成。

## 收尾判定与限制

- 原有稀疏/密集核心矩阵的 96 个进程状态和有序执行摘要均一致；稀疏 1000/10000 账户场景约 17.37x/168.58x，密集场景约 1.10x/1.21x。本次没有更改风险算法，原结果仍有效。
- 本次默认 workspace 完整测试：546 passed、0 failed、12 个已有性能测试 ignored。新增诊断 example 和全部 targets 的 feature 严格 clippy（`-D warnings`）、fmt、Python 语法检查通过。所有新对照均通过状态/响应差分。
- 在这个风险热路径优化范围内，目标完成，可以进入评审和与主目录核心优化的集成回归；本次变更按冻结基线整理为独立本地提交；尚未推送、未合并。不能提前声称与主目录正在进行的其他改动已完成集成验证。
- 整服务 40 step/s 资格仍未获得。此诊断固定调度和分配器计数下，700 步 HTTP 总耗时中位数为 40.18→47.33 秒，基线范围 32.37–77.44 秒、优化版 28.20–61.60 秒，不能证明整服务稳定吞吐提升，名义中位数也没有改善。这与核心固定工作收益是不同结论；真实异步容量、长期运行和 PostgreSQL 仍需另行资格测试。
