# Bot 大规模运行：余额候选状态按需复制

本轮先完成[交易前预占核对变更跟踪](2026-10-09-dirty-reservations.md)，再处理候选状态复制。本报告记录第二部分及最终组合版本的验收。

## 修改

`VenueAccountStore` 的外层账户索引仍为 BTreeMap，每个账户的资产余额表改为 Arc 共享。候选状态克隆只增加引用；唯一的可变余额入口通过 `Arc::make_mut` 分离当前账户。未触及的账户不再逐笔复制资产键和值。

普通余额增减、冻结、释放、转账、资金费和清算都经过同一可变入口。候选失败后原始账户仍不变；序列化保持原有普通 JSON 映射，不引入持久化引用或新 schema。复用了现有 serde rc 特性，无依赖调整。

这只减少场所余额表复制，未消除外层索引、订单簿、市场账户和调度状态的复制；同一房间写入仍需有序。

## 验证

- 全工作区 488 项通过，4 个性能测试默认忽略；本轮两个新性能测试分别单独运行。
- 核心包严格 Clippy、修改文件空白检查通过。
- 新增候选隔离测试：两个账户分别冻结/改余额，第三账户保留共享；失败冻结不污染原始状态；旧版普通映射 JSON 可读取并保持相同输出。
- 前一部分的逐笔订单、真实资金费、转账、恢复差分测试在最终组合实现上再次通过。

本轮未另做 PostgreSQL 重启或长时间比赛验收；不能把单元测试或短压测当作这些验收。

## 复制成本

每轮为 1000 账户、每账户两种资产，重复复制 1000 次，每次写两个账户。旧路径为原普通嵌套 BTreeMap 的克隆和直接写入；新路径为完整 VenueAccountStore 的克隆和冻结 API。两块均按旧/新/新/旧/旧/新/新/旧交替。

| 块 | 旧中位数 s | 新中位数 s | 下降 |
|---|---:|---:|---:|
| paired-a | 0.135514 | 0.025412 | 81.2% |
| paired-b | 0.138118 | 0.025266 | 81.7% |

这是余额表复制加两账户修改的局部工作量，不是整个 actor 复制、整笔交易或整服吞吐提升。新路径包含冻结 API 检查及快照返回，旧路径只做原映射写入；没有把这一局部结果外推到比赛容量。

**500 bot 加速场景的时钟步速在本轮对照中下降，整体吞吐收益未确认，不能宣称整服性能无回退。** 旧版两轮约 18.8/18.0，新版约 14.9/10.8 步/秒。此前同机同配方的旧版波动也明显，但这不构成排除本轮回退的证据。此异步场景每次实际执行的工作序列不同，尚缺按实际提交决策/订单计量的可比吞吐证据，原因仍待定位。

实际整服 actor 克隆平均计时从旧版约 137/141 us 降到新版约 90/99 us；这一数据支持局部复制改善，但各次工作量不同、计时嵌套，不等于独占 CPU 或端到端收益。

最终 1000 bot 实时短测约 0.971 步/秒，下单/撤单 P95 92.1/90.2 ms，无请求及 bot 错误，1000 个 bot 均已有观察；暂停快照最大落后 1 步，满足现有短测步速和请求延迟阈值。不是多小时或万 bot 容量认证。

所有任务专属压测进程已结束；本轮没有启动 PostgreSQL，也没有替换现有用户服务。
