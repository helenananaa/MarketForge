# 调度增量日志：吞吐、内存与恢复验证

接续 `2026-10-09-bot-capacity-fix.md`。这轮完成分批提交后调度状态日志过大的修复，
没有改变 bot 到达参数、资金、订单 TTL、风控判断或实时 128 个结果的提交上限。

## 实现与兼容性

原来每次时钟推进和每批 bot 结果，都把所有 bot 的模板、配置和运行状态再次
写入 `SchedulerProgress`。分成小批次改善了交互延迟，却放大了全量日志。

新增 `SchedulerDelta`，保存调度器元数据和实际变化 bot 的运行状态／未完成动作。
不重复保存未变化 bot 或完整策略模板。调度状态增加默认值为 0 的 `revision`；
增量携带基线版本，应用前验证连续版本、房间、数量、索引边界和索引唯一顺序。
缺失基线、版本断档、重复应用或畸形补丁均报错，不静默恢复不完整状态。

完整状态仍用于安装／更换调度器、手动推进、房间检查点和每 100 个调度版本。
配置或成员列表改变时也回退到完整状态。日志和动作仍在同一原子提交内；失败
不会把新版本或 bot 状态发布到内存。控制请求的幂等响应包含实际提交的版本。

新增数据库 migration 0016。快速恢复视图同时读取最新完整调度基线及其后所有
增量，独立于交易房间快照的边界。旧完整状态日志保持可读，旧状态缺少 revision
时按 0 处理；旧服务器不支持新的 mutation kind，不能直接降级读取新日志。
用户现有运行服务／数据库未切换，迁移只在本任务的独立验证数据库执行。

相关代码：`exchange-server/src/scheduler_delta.rs`、`journal.rs`、`lib.rs`，
`exchange-server/migrations/0016_scheduler_deltas.sql`，以及核心 `SchedulerState`。

## 可比短时压力

沿用冻结模板和 seed 7，每档独立 Release 进程；预热 3 秒、测量 20 秒。
500 bot 每 25ms 推进 1000ms 市场时间，目标为 40 倍速；1000 bot 使用 1000ms
间隔，目标为实时。实验与本任务编译及其他压力测试串行，用户已有服务保持运行。
以下压力场景使用内存日志，不代表 PostgreSQL 吞吐。

| 场景 | 步/秒 | 下单 P95 ms | 撤单 P95 ms | 行情 P95 ms | 峰值 MiB |
|---|---:|---:|---:|---:|---:|
| 500 bot，新版 A | 10.12 | 89.1 | 93.4 | 79.9 | 337.3 |
| 500 bot，上轮版本轮复测 | 6.01 | 59.7 | 75.3 | 89.3 | 747.1 |
| 500 bot，新版 B | 11.87 | 70.0 | 63.8 | 53.8 | 360.4 |
| 1000 bot，上轮版此前测试 | 0.913 | 213.3 | 285.3 | 293.8 | 456.8 |
| 1000 bot，新版本轮测试 | 0.961 | 133.1 | 159.8 | 119.7 | 179.7 |

500 bot 按新版 A → 旧版 → 新版 B 顺序交错，吞吐约为邻近旧版的 1.68～1.98 倍。
新版处理了更多仿真步骤，峰值内存仍明显更低；相同墙钟窗口不是等步骤或等成交量。
下单 P95 并非所有测试都改善，新版 A/B 的下单 P95 均高于这次旧版复测，因此
不能宣称所有延迟指标单调下降。所有上述测试探针错误为 0。

1000 bot 达到脚本的 95% 实时时钟阈值，下单／撤单 P95 均低于 250ms；本轮
33/32 个下单／撤单样本仍只是短测。旧版 1000 bot 是前一轮数据，没有在本轮
做同人数交错重测。500 bot 仍未达到 40 倍速，万级 bot 和长时间比赛容量未验证。
bot 获得过观察不等于持续下单，资金和风险限制也会影响活跃订单数。

新版 A 平均占用约 1.48 个逻辑核，旧版复测约 1.26；机器有 32 个逻辑处理器。
减少序列化后吞吐改善，但全局写入串行和全账户风险检查仍限制多核利用率。

## 同工作量的日志与恢复

38 bot 的真实 PostgreSQL 场景推进到 110 步，暂停并重启数据库及服务，恢复后
账户观察、订单、消息、时钟和调度状态完整 JSON 完全相同；继续推进到 130 步。
两次独立实验均通过，测试使用压缩消息／POV 时间线，不能当作真实市场校准。

直接读取第二次实验的实际调度日志，再把同一批记录逐条还原为完整状态计算 JSON
大小：6 条完整记录、375 条增量记录共 5,497,235 字节；若每条保存完整状态则为
24,009,579 字节，减少约 77.1%。这是同一交易轨迹的调度 JSON 口径，不包括
交易日志、索引、WAL、数据库页和网络协议，不能解释为数据库总体缩小 77%。

另在真实 PostgreSQL 事务内临时移动恢复 head、查询恢复视图后回滚，模拟交易
快照晚于调度基线。视图返回的调度基线和增量链与原日志尾部精确一致，确认不会
因交易快照边界而漏掉必要增量。临时更新已回滚，数据库与验证服务均已停止。

回执：`postgres-recovery/`、`postgres-recovery-boundary/`、
`postgres-journal-summary.json`、`boundary-journal-summary.json` 及原始日志 JSON。
本轮未做大量 bot 的 PostgreSQL 吞吐或大型旧数据库迁移时间测试。

33 bot 原时间线另完成 1000 步，耗时 24.984 秒、峰值工作集 165.8MiB，两个 POV
任务均成交 25 单位，无 bot 错误。未延长 TTL，保持既有 173.08 秒／512MiB 限额；
暂停时最后观察落后时钟 1 步。上轮同规格约 310MiB，本轮降低，但实时完成顺序
使两次交易路径并非逐笔相同。这仍只有约 25 秒墙钟时间，不能证明长期内存有界。
回执 `long-1000/report.json`。

## 回归与剩余工作

全 workspace 476 个 Rust 测试通过，包括旧 JSON、增量连续性／拒绝损坏状态、
成员变化回退完整记录、200 bot 分批不丢决策、检查点间时钟／订单恢复、幂等请求
和实时训练状态恢复。全 workspace/all-targets Clippy `-D warnings`、格式和本轮
涉及文件的 whitespace 检查通过。Clippy 最初指出新增测试的初始化写法，已修复，
失败回执保留。这些结果不替代工作区其他并行改动的发布验收。

这轮没有直接让所有等待中的 bot 跳过 tick：`MarketBot::decide` 在到达时间检查
之前，还更新价格／波动率、处理消息、检查挂单 TTL、止损和强制减仓。直接按
`next_decision_ms` 跳过会改变风控和策略结果。

后续事件调度应先分离“必须随市场更新的轻量状态／风险检查”和“到期后的策略
计算”，再为成交、消息、标记价与订单到期建立可靠唤醒机制。还需逐步消除每单
全账户扫描、按房间隔离写入状态，并建立日志保留／归档机制。增量日志减少了
增长速度，尚未使历史日志总量有界，也没有实现这些后续架构项目。
