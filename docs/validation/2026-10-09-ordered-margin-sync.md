# 有序批量保证金同步与轻量账户输入

接续 `2026-10-09-incremental-perp-risk.md`。上一轮缩小了永续订单执行后的同步范围；本轮继续减少执行前全组同步的重复查找和快照构造，仍遍历并核对每个账户，不放松风险条件。

## 实现

- 跨市场上下文只读取账户 ID、本市场未实现盈亏、初始/维持保证金、订单预留和持仓是否打开。内部使用轻量输入，避免为这些字段构造完整的公开账户快照和复制双向持仓腿；公开快照接口保持不变。
- 密集同步按 ID 合并遍历账户、成功校验缓存、上下文和保证金状态四个有序表。只有账户全部字段、现金、订单预留内容、配置、标记价格、上下文、当前保证金状态均精确匹配时才跳过重复计算。缓存未命中仍调用原有风控/保证金计算。
- 请求数量少于账户数量的四分之一时使用原索引路径，避免稀疏更新反而扫描全表；重复或乱序请求也按原顺序逐个处理。
- 内部同步不再复制一个随即被丢弃的返回快照；公开同步 API 仍返回原类型。缓存命中但上下文/状态缺失或不同时仍修复这些条目。
- 保留失败顺序和交易回滚：构造后续请求失败时，先按原顺序处理已经构造的账户请求，保证早先同步失败仍优先返回。批处理中的错误保留与逐账户同步相同的已执行前缀。

没有引入持久化格式、配置开关或新依赖。测试参照和性能开关只存在于 `cfg(test)`，不进入服务运行时。

## 等价性

原完整快照、逐账户同步算法保留为测试参照。上一轮的 360 条逐笔交易差分测试，现在直接对比新批量路径与原同步算法，同时覆盖单向/双向持仓、撤改单、TTL 到期、资金不足、价格改变和序列化恢复后继续交易。

新增测试对比轻量输入与完整公开快照，包含净头寸为零但仍有双向敞口、不同价格、跨市场上下文和恢复。批处理另外与逐个公共 API 调用对照：全冷、全命中、混合失效、上下文缺失、状态过期、溢出、稀疏更新、重复/乱序请求以及恢复；比较结果和完整持久化状态。

## 固定工作量测量

同一个 release 测试进程，1000 账户、两个永续市场、600 条完全相同订单。两边都启用上一轮的执行后增量范围，仅切换本轮的同步算法。每块按旧/新/新/旧/旧/新/新/旧交替，共两块、16 次运行，执行结果及完整最终状态全部相同。

| 测量块 | 原算法耗时中位数 s | 新算法耗时中位数 s | 耗时下降 | 原/新保证金同步中位数 ms |
|---|---:|---:|---:|---:|
| paired-benchmark | 0.792744 | 0.475069 | 40.1% | 393.61 / 142.62 |
| paired-repeat | 0.856117 | 0.475235 | 44.5% | 407.47 / 143.43 |

这组固定交易工作耗时减少约 40～45%。计时可能嵌套，不能把各阶段相加当作独占 CPU 时间；结果不代表比赛 bot 容量相应增加。参照保留原完整投影和逐账户调用；其公共同步 API 与新路径共用已验证的标量风控实现。

最初只改轻量投影/返回快照时收益约 3%，不足以单独下结论。独立二进制前后运行曾出现较大外部负载波动，相关原始记录保留，但没有用来宣称收益；最终结论采用上面的同进程交替参照。

```powershell
cargo test -p exchange-core --release ordered_margin_sync_fixed_work_benchmark -- --ignored --nocapture
```

证据目录：`.local/bot-margin-inputs/`，包括 `paired-benchmark.log`、`paired-repeat.log`、`paired-summary.json`、源码修改前副本和补丁。

## 完整服务与同场对照

所有服务均为任务专属进程、随机本地端口，recipe 冻结为上一轮相同配方，seed=7；每例预热 3 秒、测量 20 秒，未增加策略等待或延长 TTL。没有替换用户现有服务。

初始工作区 release 测量如下。它与上一轮历史服务数据并非同时同源，不能把差值全部归因于本补丁：

| 场景 | 步/秒 | 下单/撤单 P95 ms | 峰值 MiB | 最终观察中位/最大落后步 |
|---|---:|---:|---:|---:|
| 500 bot，25ms | 16.734 | 67.96 / 74.92 | 228.74 | 11 / 15 |
| 1000 bot，1000ms | 0.953 | 105.64 / 97.39 | 198.50 | 1 / 1 |

随后冻结两份完整源码，逐文件核对只有本轮 `actor.rs`、`perp.rs`、`trading.rs` 不同；依赖、服务代码、配方一致。在任务专属 target 中分别编译，并验证二进制哈希不同。最初构建缺少被 include 的配方，以及一次 Cargo 共享 target 缓存复用的产物均未用于对照；修复后保留独立二进制和构建日志。源码清单见 `controlled-source-hashes.json`。

500 bot 按旧/新/新/旧运行；最后追加一组 1000 bot 实时比较。最后的新 1000 例因执行会话中断未产生报告，已使用新的输出目录完整重跑，未覆盖已有成功结果。

| 同场运行顺序 | 步/秒 | 下单/撤单 P95 ms | 峰值 MiB | 最终观察中位/最大落后步 |
|---|---:|---:|---:|---:|
| 旧 500 A | 11.413 | 76.26 / 80.38 | 190.59 | 10 / 14 |
| 新 500 A | 12.932 | 63.83 / 76.23 | 205.93 | 10 / 14 |
| 新 500 B | 19.360 | 59.32 / 59.42 | 231.10 | 11 / 15 |
| 旧 500 B | 20.263 | 55.58 / 54.89 | 223.04 | 10 / 14 |
| 旧 1000 | 0.970 | 101.16 / 127.03 | 189.49 | 1 / 3 |
| 新 1000 | 0.955 | 46.43 / 48.38 | 192.80 | 1 / 1 |

**整服吞吐提升尚未稳定证实。** 500 组旧版自身的步速就从 11.4 变到 20.3，新版从 12.9 变到 19.4；不能据此宣称整服获得固定交易测试的 40% 提升。1000 组新版该次请求延迟较低，但仅是一组短测。这里的步速是市场时钟速度，不是成交或策略决策吞吐。

所有成功测量均无请求和 bot 错误，全部 bot 已有观察。最终观察来自暂停快照，不是整段运行的延迟分布；500 加速组仍最多落后 14～15 个仿真步，目标 40 步/秒未达到。1000 组新版本两次测量均满足现有 95% 实时步速和下单 P95 <250ms 阈值。每类请求约 33～36 个样本，不能认证多小时或万 bot 比赛容量。

缓存输入频繁因价格/账户变化失效时，原有风险计算仍必须执行，所以真实收益取决于可复用输入的比例。执行前全账户遍历、场所账户检查、候选状态复制和串行写入仍在；本轮没有完成房间隔离、多核提交或事件驱动策略唤醒。
