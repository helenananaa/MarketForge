# 房间执行锁的固定工作量压测

测量日期：2026-10-10。独立 worktree：`E:\CodexData\worktrees\room-lock-load\MarketForge`，分支 `codex/room-lock-load`，基线 `71b58e9`。主工作目录的未提交撮合、账户和策略优化没有复制到此 worktree。本报告记录优化前基线：该阶段只增加压测工具和默认关闭的计时 feature，没有实现执行分区，也没有替换已有服务。后续实现和对照见同目录 `2026-10-10-room-lock-optimization.md`；2026-10-11 将两阶段相关源码、工具和报告一并整理为本地提交。

## 方法与证据边界

每组独立启动 Release 服务，只绑定随机 loopback 端口，使用独立工作目录及内存 journal。没有接入现有服务或数据库。Rust Tokio/reqwest 客户端用持久 HTTP 连接，任务通过 barrier 同时开始，每个任务使用独立有限资金账户。

拓扑包括单房间单订单簿、单房间四订单簿、四房间各一订单簿，以及单房间四独立 venue。每个房间初始化相同数量的账户，活跃账户路由随拓扑改变。品种使用相同 BASE/QUOTE 标识，测试共享 venue 资金和永续保证金组；不同 venue 的余额独立。

并发档位为 1、8、32。账户人口随并发档位增加，结论应在同一并发档位内比较。每任务预热两轮；测量固定 2048 个业务循环。挂单撤单每循环两个请求，共 4096 请求；成交往返每循环四个请求，共 8192 请求、4096 笔真实成交。零手续费用于验证完整资金恢复；没有运行时补充资金或放宽订单风险约束。

各矩阵顺序运行两轮，第二轮反转测试顺序。记录全部请求回执、资金快照、最终订单簿、服务指标、进程 CPU、峰值工作集，以及后台进程 CPU 和编译重叠采样。编译重叠组保留原始回执，从主要吞吐对照中排除。无编译重叠也不等于机器空闲；后台应用和其他任务仍然运行，不能把这里的吞吐作为独占机器容量。

这是闭环固定工作量短时测试，不是固定到达率压测。请求尾延迟不能当作生产 SLO；跨房间拓扑还改变了快照大小及每个房间的历史长度，因此性能差异不能全部归因于 mutex。

## 计时语义

`bench-execution-timing` feature 默认关闭，普通构建没有新增计数器。压测构建记录目录等待、房间等待、持锁时间，以及普通 HTTP 订单的 prepare/apply/receipt/journal/publish 阶段。

- `prepare` 包含持锁后的权限查询、风控前置准备、候选状态及盘口构造。
- `apply` 包含完整网关和核心状态变更，不是裸撮合算法耗时。
- `journal` 包含执行记录构造、排队和 journal 确认，不是数据库磁盘耗时。
- `room_held` 包含退出时的已提交快照发布；publish 阶段不包含 guard 的析构。
- 所有计数器是累计墙钟时间及均值，包含调度等待，不是 CPU 时间或阶段 P95。单阶段 max 包含预热，字段名明确标注。

计时 feature 有自身成本，本任务不把插桩构建当成未经插桩的生产容量。源码与二进制 SHA256 保存于配套 JSON。

## 受控等待耦合实验

在 BENCH-0 的手动 `/clock/step` 中运行休眠 750ms 的本地测试插件。确认插件已进入后，并发提交 BENCH-1 订单、另一房间订单，以及当前房间已提交行情读取。三次重复结果：

| 请求 | 延迟范围 ms |
|---|---:|
| 同房间另一品种订单请求 | 758.16–759.46 |
| 另一房间订单请求 | 1.75–2.08 |
| 同房间已提交行情读取 | 0.67–12.21 |

手动步进要求房间暂停，因此同房间订单在等待后返回预期的 `market paused` 拒绝；另一房间订单正常接受。这个实验验证请求处理边界的等待耦合，不能说暂停房间发生了成交。也不能外推为自动 bot 计算会持锁：自动计算仍在锁外。

证据：`target/room-lock-load/head-of-line-final/`。插件只存在于忽略的 target 输出目录。

### 可以确认的结论

同房间四品种的正常订单也出现明显队列等待，远大于持锁后完成单个事务的时间。32 并发时，`room_wait / (room_wait + room_held)` 约 97%，这是服务端两个计时段的比例，不是完整 HTTP 响应时间比例。同房间四独立 venue 的现货成交仍出现约 9.7–9.9ms 平均锁等待，说明独立 venue 的普通订单也被房间执行边界合并。

四房间成交对照使用约 3.5–3.9 个 CPU 核，而同房间使用约 1.3–1.5 个核，单房间写路径没有有效利用更多核。已提交行情在这些成交组的读取 P95 约 1.3–3.2ms；其他短组读取尾部最高约 24ms。没有把读取路径称为绝对不受后台负载影响。

永续同房间成交的持锁均值约 0.370ms，其中网关/核心 apply 约 0.171–0.172ms，journal 阶段约 0.093–0.095ms，prepare 约 0.047–0.048ms。缩短临界区及优化核心状态变更仍有价值；换成 actor 但保留整个房间单执行者，也仍保留这条串行吞吐上限。

### 尚未证明的结论

跨房间成交吞吐约为同房间的 2.7–3.6 倍，但同时改变了每事务状态大小、历史分布和共享保证金范围，不能声称“拆锁必然获得同样倍数”。本任务没有实现品种或 venue 分区，没有对一个真实共享账户的跨分区事务、清算、资金费和恢复提供新证明。

这些结果支持下一步做受控分区原型，并优先审查 `room + venue` 是否适合作为普通订单边界；资金划转、房间时钟及跨市场事件仍需明确协调。它是待验证的工程方向，不是本轮已经完成的优化。是否进一步按同 venue 内的品种拆分，应结合账户及保证金事务设计和固定工作量对照决定。

没有测 PostgreSQL 持续写入、长期 bot 负载、开放到达率饱和点、真实交易延迟或浏览器渲染。共享机器的后台程序及其他测试进程 CPU 明确保存在回执中；无编译重叠只排除了编译这一类干扰。
