# 稀疏增量 / 密集批量保证金与强平优化

## 对照基线与隔离

- 分支：`codex/incremental-margin-risk`，独立 managed worktree。
- 主目录当时在做其他核心优化。本轮从 `71b58e9` 建立隔离目录，再冻结主目录的 51 个修改/新增文件，形成对照基线 `f3ab562`。
- 本轮 diff 必须相对 `f3ab562` 审阅。这个本地快照包含已有的核心、服务与策略改动，其收益不归本轮。

- 本轮没有编辑主目录，也没有推送远端。

## 实现

1. 维护账户输入变化集合，以及本地价格依赖和持仓账户的派生索引。成交、订单预留/撤销、资金变动、跨市场风险上下文、资金费和强平队列变化进入失效范围。
2. 已知变化范围小于该市场/跨保证金组账户数的四分之一时，按升序同步所选账户；达到阈值或范围未知时，用既有全量批处理。
3. 价格变化只处理本地价格依赖账户和尚未验证的输入；同价更新只处理脏输入。双向账户根据两条腿判断价格依赖，不能用净仓为零代替无敞口。
4. 全仓组把所有同报价资产市场、venue 余额及待强平集合的变化取并集。无脏输入可跳过同步；成功完成整个组后才确认基线。
5. 密集批次开始时标记范围未知，避免批处理内再为每次写入构建脏账户树。现金同步不改变持仓/订单索引，直接更新现金，保留原有失败回滚和风险计算。
6. 强平首次候选发现仍检查当前权益和维持保证金。稀疏持仓索引缩小候选范围；队列逐项重试直接检查该账户，不为每个候选重建整市场名单。
7. 所有新增追踪数据都 `serde(skip)`，恢复后未知，先完成原全量路径才复用增量结果。索引在首次读取时重建；恢复修正本地预留时，下一次组同步继续全量，保持旧的修正顺序。

## 保持的行为与边界

- 没有修改盈亏、初始/维持保证金、跨市场抵押、资金费、风控拒绝、强平执行或损失分配公式。
- 保留逐命令价格更新、订单保护/到期、两阶段保证金及状态更新、升序错误/事件顺序、命令序号分配和失败前缀行为。
- 强平使用当前账户数据计算，不能以缓存的 `margin_status` 决定资格。
- 未变更持久化结构或恢复接口；失败不能建立“已同步”的派生基线。
- 本轮没有重写多市场的逐目标聚合算法。密集跨市场计算仍有随市场数增长的原有成本；没有跨时钟合并价格事件或降低检查频率。

## 差分验证

测试专用 `full_scan_reference()` 强制原有全量范围、原有价格缓存条件和原有整表强平检查；同一动作分别进入自适应与参考路径。每一步比较返回结果、事件/执行顺序以及完整持久化状态。公开 benchmark 进一步对真正的冻结版本二进制比较状态和执行记录 SHA-256，避免仅依赖同一实现内的参考开关。

新增六项测试：

- 4 组单向/双向 × 关联/独立市场，各 256 步，共 1024 步真实交易、订单、资金费、余额、时钟、风险拒绝及定期恢复。
- 冷恢复、旧预留修正、全仓余额不足、失败后的命令序号和回滚顺序。
- 2/32/128 个活跃账户 × 单向/双向，各 48 步，共 288 步稀疏/阈值/密集及同价更新；包括零净仓双腿敞口与跨市场风险状态。
- 溢出失败前缀、连续重试、修复后恢复一致。
- 单向/双向各 12 步 room 级强平：无深度排队、跨市场撤单/冻结、补款、真实部分成交、部分强平后恢复及最终清队列；比较历史与恢复附属字段。
- 旧检查点可反序列化的异常带符号双腿，其合计为零时仍按原计算处理，不能误用价格无关缓存。

最终 `cargo test --workspace`：546 passed、0 failed、12 ignored。ignored 是既有需单独运行的受控 benchmark；不是本轮差分测试。首次服务进程测试因 Windows Store `python3` 占位程序导致 4 项失败，记录保留；使用主项目现有 `.venv/Scripts` 加入当前测试进程 PATH 后完整通过，没有修改机器人 manifest 或测试门槛。

`cargo clippy --workspace --all-targets -- -D warnings`、`cargo fmt --all --check`、新增 include 测试文件 rustfmt 检查和 `git diff --check` 均通过。benchmark 的返回值枚举有一个有说明的 `large_enum_variant` 局部豁免，避免计时区新增每命令堆分配；生产风险索引集中放在派生结构中，未扩大 `MarketEngine` 枚举。

## 核心固定工作性能

使用 `exchange-core/examples/benchmark_margin_risk.rs` 与 `scripts/benchmark_margin_risk.py`。

- 每个场景按 `before, after, after, before` 交错运行两轮，每版本 4 次，报告中位数。
- 同样的账户、持仓、市场、动作和步数；显式恢复持仓 fixture，预热后计时。
- 初始化、恢复与最终序列化不计入热路径时间。真实成交/恢复行为由上面的差分测试另行覆盖；订单负载本身也发生真实成交。
- 每次运行比较规范化完整状态（只排序无业务次序的 `seen_order_ids`）和有序执行记录，任何差异立即停止并保留产物。
- 二进制/结果哈希、每轮原始计时和阶段计数见 JSON 汇总。机器上其他用户进程保持运行；这是本机有界对照，不是独占硬件容量认证。

## 整服务负载边界

后续已完成 view/内存同进度复核，见 [`2026-10-10-margin-view-memory-followup.md`](2026-10-10-margin-view-memory-followup.md)。700 步存活堆 223.07→222.85 MiB、进程峰值 working set 396.66→397.74 MiB（约 +0.27%）；原墙钟对照的约 75% 内存增长未复现。普通 view P95 29.83→30.28ms，固定状态快照构造/编码未回退；永续端到端仍有残差，未声称全部尾延迟已解决。以下保留原墙钟数据和当时的限制。

整服务对照使用现有 `scripts/benchmark_market_load.py`，隔离子进程、随机 loopback 端口和独立工作目录。冻结同一个 seed=7 的 38-bot 模板，扩展为 1000 个合成机器人；每轮 3 秒预热 + 20 秒观察，配置 25ms/step（40 step/s），ABBA 两轮、每版本 4 次。

| 指标（各轮统计的中位数） | 基线 | 本轮 |
| --- | --- | --- |
| step/s | 16.27 | 31.13 |
| 每轮 step/s 范围 | 5.95–30.15 | 24.36–32.14 |
| 下单 P95 ms | 85.01 | 42.67 |
| 撤单 P95 ms | 72.03 | 56.83 |
| view P95 ms | 21.59 | 28.13 |
| 平均逻辑 CPU 核数 | 1.16 | 1.23 |

8 次生成的 recipe 哈希完全相同，最终每次均有 1000 个机器人收到观察。**步频中位数的名义提升约 91%，但基线慢轮与较大的轮间波动影响明显，不能把它作为稳定的服务吞吐倍数。**固定步频与 HTTP 探针涉及调度、机器人、事件历史和服务端成本，不能直接把核心固定工作倍数当成 HTTP 吞吐或生产容量倍数。

服务结果有两个明确限制：

- 两版本都未达到脚本要求的 38 step/s（目标 40 的 95%），这次仍没有取得 1000-bot 的 40 step/s 容量资格。8 轮无请求错误；基线有一轮下单 P95 为 494.43ms，超过既有 250ms 门槛。本轮 4 次下单/撤单 P95 均在门槛内。view 中位 P95 有回退，见表。
- 本轮峰值内存中位数更高；固定墙钟下执行了更多步骤，保留的历史与调度状态量也不同。这不是同进度的内存对照，既不能把全部增长归因于风险索引，也不能据此声称没有内存回退。峰值均低于既有 1024MiB guard；完整逐轮进度/内存记录保留在 JSON 与原始证据中。
