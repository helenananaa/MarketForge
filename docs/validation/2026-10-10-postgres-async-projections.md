## 变更范围

成功应答仍等待主日志事务提交，再安装候选内存状态并发布事件。幂等键、外部操作配额、房间写入 fencing、订单/成交身份键、恢复快照及调度状态继续同步提交。执行记录采用集合插入；订单、事件、成交、行情 tick、账户流水、持仓和转账查询表由独立连接后台批量投影，每批最多 256 条执行及 256 条转账事件。

事务内持久化待投影引用；查询表更新、进度和引用删除同事务提交。投影失败整体回滚，重启继续处理。恢复从主日志和同步身份键获取最新 tick / 下一订单 ID，恢复不依赖查询表先追平。查询 API 捕获入口时已提交的有限待处理范围并等待，超时 30 秒返回错误；包含 K 线查询，保留原授权过滤。待处理队列每房间上限 65,536 行，超限在发布前拒绝新提交。

迁移 0018 为既有查询数据建立同步身份注册和进度；旧、新写入二进制混用不属于支持的升级方式。详细行为见 `docs/ASYNC_QUERY_PROJECTIONS.md`。

本任务实际实现为三份既有源文件加三个新文件，清单见 `.local/pg-async-study/implementation-manifest.json`，相对于测量基线的独立补丁见 `implementation.patch`。工作树复制了已有未提交改动，未把它们计为本次实现；此前的 3536 文件快照对照确认其余既有源文件未被本任务改变。

## 对照方法

沿用 `.local/pg-write-study/run_study.py` 的操作序列、recipe 和随机种子，包装脚本为 `.local/pg-async-study/paired_study.py`。测试 PostgreSQL 18.4，独立任务数据库，`fsync=on`、`synchronous_commit=on`、`full_page_writes=on`；没有关闭持久性来换速度。一次只启动一个被测服务。

固定轨迹按前/后/后/前交替，每轮 4 个预热块、160 个测量块，共 1340 请求、320 次成交，包括挂单、成交、改单、撤单、风险拒绝、手动推进和转账。连续 bot 负载每轮预热 5 秒、测量 60 秒：38 bot 常速各一轮；500 bot/25ms 与 1000 bot/1000ms 各版本两轮，顺序前/后/后/前；另有 memory 存储各版本一轮对照。

500/1000 bot 使用同一 38 bot 模板加噪声 bot，spot/perp 有限资金，不能视为 500/1000 个均衡、永续活跃策略的容量认证。固定轨迹用于语义逐项等价验证；实时调度因决策时间和实际完成工作量变化，轨迹不要求逐单相同。表中多轮结果为每轮指标的中位数，P95 是各轮 P95 的中位数，未冒充合并样本 P95 或置信区间。

基线二进制 SHA256：`2dad39e126bcb4cf5ff651a0362cd9751acd52774f50217c19e528f731745bb7`。

改后二进制 SHA256：`80882840c89a8b66452da88ae780a049e8deca4a87890143ec4bdefe5d4a0f69`。最终测试、崩溃恢复资格验证、性能对照均使用此冻结实现。

## 剩余瓶颈和回退解释

高负载下主动下单 P95 回退：500 bot 约 +85%，1000 bot 约 +28%。撤单 P95 改善，吞吐上升，但这不足以认定下单尾延迟问题已经解决。现有下单和调度持有房间状态执行所有权直至持久化完成；订单 ID 分配本身是原子 CAS，不是全局事务锁。更快的自动推进增加了每秒执行工作和竞争，这是待验证的尾延迟原因，当前采样尚不能量化归因。

同步 actor 快照依然昂贵：例如第二轮改后 1000 bot 测量窗口内，17 次快照 INSERT 的 PostgreSQL 执行时间总计 1.76s、平均 103ms/次，并产生约 19.4MB WAL；同步 room_mutations 992 次，总执行约 0.88s。这些是 SQL 执行统计，不等于端到端等待，不能与墙钟阶段直接相加。下一步应对房间排队、编码、快照、SQL 和提交分别打点，再评估快照提交策略和自动工作与外部订单的调度公平性。

## 幂等与恢复验证

- 最终 workspace 测试：542 通过、12 忽略、0 失败；严格 workspace/all-target clippy、格式及 diff 检查通过。
- PostgreSQL 实测筛选：7 测试通过（6 个真实数据库测试、1 个相关内存路由测试），保持持久性选项开启。
- 投影阻塞时主日志照常提交；幂等查询、配额、同步订单身份冲突校验有效；恢复下一订单 ID 不依赖查询表。
- 注入查询表约束失败：查询投影事务整体回滚、待处理引用保留，解除故障后恢复；另验证跨房间先分配序号后提交的记录不会被全局进度游标跳过。
- 外部资格脚本先阻塞投影，执行 spot/perp 订单，再强停服务并重启独立数据库；重启服务时继续阻塞投影，恢复状态哈希相同。4 次幂等重试均返回原响应、不新增执行记录；放行后待处理 6→0，查询结果完整。
- 初次真实 PostgreSQL 测试揭露 K 线查询缺少屏障，已补齐并重复通过；失败日志保留。

测试限制：既有 control_idempotency PostgreSQL 重启测试在测试运行时销毁期间仍有 agent 线程 Tokio timer panic 日志；断言和退出码通过。这属于测试后台任务生命周期现象的判断，未宣称日志零 panic，未在本任务扩大修改生命周期。独立服务强停/数据库重启验证通过，不依赖该测试的退出清理。
