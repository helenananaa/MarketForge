# 大量 bot 仍慢的原因：当前版本拆阶段诊断

检查版本：`173c2e54ab29b4d9660c7c745dd6be24fe9313c2`。本轮仅调查，生产源码没有修改。
诊断源码和可执行文件保存在 `.local/bot-performance-study/`，不替换运行服务。

结论：当前原生 bot 场景主要受串行状态事务限制。策略计算本身很轻；完整调度器
反复复制、房间执行历史反复复制/释放，以及无订单动作的决策仍走完整提交路径，
共同占用写锁。已有账户索引、保证金缓存、余额共享和增量日志没有消除这些路径。

## 确认的热点

### 1. 并行计算完成后等待串行提交

`exchange-server/src/realtime.rs:422` 在全局 AppState 锁下准备观察；计算在
`spawn_blocking` 中进行。`lib.rs:9528` 的提交再次取得同一个锁，并持续持有到
日志提交和候选状态安装完成。`ServerState.app` 是整服的 Mutex，不是每房间一个。
因此不同房间也共享这一入口；多房间争用的程度本轮未运行测量。

500 bot 第一版诊断：57140 次计算，56704 次进入有效状态提交；策略计算计时
累计 0.108 秒，平均约 1.90 微秒/次。实例创建累计 1.847 秒，快照 0.400 秒。
已完成结果至开始应用平均等待 500.6ms、最大 748.2ms；这是结果等待，排除了
观察构造及策略计算。1000 bot 实时组相同口径平均 836.9ms。

500 bot 细分诊断：调度事务持锁累计 52.418 秒，平均 36.0ms/事务左右（精确
调用数见 metrics），不包含观察准备的锁占用。下面阶段互斥并处于该持锁区间：

| 调度事务阶段 | 累计 s |
|---|---:|
| 获取并复制整个 SchedulerState | 6.486 |
| 复制整个 RoomManager | 10.790 |
| 应用时钟或 bot 动作 | 12.907 |
| 构建调度增量/完整日志输入 | 3.819 |
| 日志提交等待及处理 | 2.332 |
| 发布新状态 | 15.985 |

执行记录构造、快照及其余检查占剩余小部分。前三类状态复制和发布合计约
33.26 秒，占调度持锁计时约 63%。核心保证金/预留等计时位于动作应用内部，
且包含人工探针工作，不能再加到这个分解上。

### 2. 房间层历史仍全量复制，旧历史也在锁内释放

`exchange-core/src/room.rs:24` 的 RoomManager 仍自动派生 Clone，字段
`executions: BTreeMap<RoomId, Vec<ActorExecution>>` 保留完整执行历史。
`lib.rs:9591` 每个 tick 和每批结果都克隆整个 RoomManager，即使这一批没有
任何订单动作；`lib.rs:9825` 用候选状态替换旧状态，旧 Vec 在写锁内析构。

市场引擎 command/event/clearing history 使用分块共享，但没有覆盖这个房间
执行历史 Vec。细分诊断只将原派生 Clone 等价展开，并分别计时各字段：所有
RoomManager 克隆中的房间状态部分累计 0.817 秒，执行历史部分累计 11.611 秒。
两项包含人工订单事务，范围大于上表的调度事务；执行历史占这两项约 93.4%。

按相邻约五秒窗口归一到调度批次数，历史复制从首窗约 0.92ms/批升至末窗
12.94ms/批，而房间当前状态复制从约 0.37ms/批至 0.64ms/批。这里核心统计
也包含探针克隆，归一口径是近似每调度批次，不是纯调度调用的独立样本分布。
源码的全量 Vec 克隆与随运行时间上升的实测成本一致。

细分发布阶段：事件缓存/广播累计仅 0.042 秒，房间候选替换及旧状态释放
5.943 秒，调度器安装及旧调度器释放 9.997 秒。不能把 15.985 秒全归到广播、
数据库或历史释放；其中调度器重复复制/替换是更大的一项。

### 3. 增量日志存在，但内存事务仍反复复制整个 bot 集合

`lib.rs:9577` 获取 `.schedulers.get(...).cloned()`，每次复制全体 bot；
`lib.rs:9829` 安装 `outcome.state.clone()`，再次复制，并释放上一个完整状态。
自动 worker 最后丢弃返回的完整 SchedulerState。大批次的候选索引缩小了结果
匹配范围，却没有消除这些全体成员复制。SchedulerDelta 构建还逐个核对模板和
运行状态。每批只提交至多 64 个 bot，但这些全体集合工作仍按 500/1000 成员做。

应先把实时返回值缩成提交确认，按实际变动 bot 安装状态/构造增量，保留配置、
epoch、运行状态版本和事务失败回滚的约束。这里只给出方向，没有实现新协议。

### 4. 没有订单动作的决策也付出完整写入事务成本

`realtime.rs:435` 每 tick 遍历可运行 bot，构建观察、复制旧状态并派发任务。
`market_bots.rs:1628` 在 decide 内部才检查下次策略到达时间；此前已经进行
行情/波动率、消息、TTL、止损和强制减仓等处理，状态可能确实改变。

500 bot 第一版诊断：56704 次提交中 43293 次没有订单动作（76.35%）；细分版
为 66.25%。第一版末段约 98% 为空，细分版最后两个窗口约 100% 为空。不能将
其全部视为可丢弃的无效工作，但目前它们仍产生全体调度器复制、房间历史复制、
版本推进和日志事务。应拆分轻量市场/风险更新与到期策略，并用可靠事件和时间
队列唤醒；直接跳过 `decide` 或不保存空动作状态会改变策略/恢复语义。

### 5. 每单全局风险工作仍存在，但不是全部成本

执行前 `actor.rs:1592` 仍同步目标现货市场所有账户，或同步永续抵押组。
`actor.rs:2114` 清算后场所合法性检查遍历全部场所账户；标记价格联动也可能
使执行后范围回退全组。成功保证金缓存只省去重复计算，不省去遍历和输入核对。
原有清算扫描还构造完整账户快照。

第一版 500 bot 诊断的执行前余额同步累计 1.872 秒，清算后场所检查 1.128 秒；
总动作应用为 11.605 秒，其他阶段另有成本。执行前同步包含保证金同步，所以
二者不可相加。此项仍应继续增量化，但不能认为再优化一个风险函数便能解决
当前几十秒的状态复制/替换成本。

## 调度公平性与指标含义

64 个结果批次限制保护人工请求延迟。结果和 tick 都就绪时交替选择，有助于
时钟不被整轮结果排空阻塞；它不保证所有 bot 每步完成。在持续过载且两者都
就绪时，大致每个时钟机会只提交一批至多 64 个结果，500 个 bot 一轮需要多个
机会，执行历史和完整状态复制还使每次机会变贵。这解释了 HTTP 已较快、时钟
仍推进，但 bot 的观察落后。每 bot 一个在途任务限制内存积压，不限制等待时间。

增加 Tokio blocking 线程不是这些热点的直接修复。计算线程开始等待平均只有
几十到一百多微秒量级，结果提交等待却达数百毫秒。当前短测没有显示计算池为
主瓶颈，也没有显示内存日志队列成为主瓶颈；不能推广到外部模型/进程插件或 PG。

建议顺序：先解决房间执行历史复制/释放与完整调度器复制/替换，随后实现有正确
失效与唤醒语义的事件调度，再减少执行前全账户扫描，并按房间隔离写入状态。
继续同时报告时钟步速、真正提交的决策/动作数量、观察年龄、队列等待和长时
内存斜率；动作数量是提交尝试，不等于成功订单或实际成交。
